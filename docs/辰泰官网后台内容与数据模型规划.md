## 1. 文档目的

本文件用于指导辰泰官网后台原型、数据库建模、内容迁移和前台 API 接入。规划以当前仓库实际页面、`data/site.json`、`public/app.js` 及 `public/assets` 为依据，同时吸收已经确认的最终页面要求。

第一阶段只建设本地后台原型，不直接修改线上网站，也不在模型未确认前购买正式服务器。

## 2. 核心结论

1. 现有网站已经不是简单的 6～8 个静态页面，实际包含企业内容、新闻、技术服务、产品、案例、工艺流程、三维演示、资质证书和询价等多类数据。
2. 内容当前分散在 HTML、`public/app.js` 和 `data/site.json` 三处，联系方式、指标及中英文内容存在多源不一致，后台建设应先实现“单一内容源”。
3. Directus 第一版不应把每段页面文案都做成独立数据表，应按“稳定栏目 + 可排序内容项 + 翻译表 + 媒体关系”建模。
4. 新闻资讯、行业资讯和技术服务可以共用一套文章模型，通过分类区分；产品、案例、工艺解决方案仍应分开管理。
5. 所有专利、资质、荣誉证书建议合并为一个 `certificates` 集合，通过分类和展示位置控制在“关于我们、科研创新、资质荣誉”等页面中的出现位置。
6. 客户留言必须通过独立安全接口写入，不能从公网浏览器直接开放 Directus 数据表写权限。
7. 工艺流程图和三维模型属于“代码型交互资产”，后台只管理标题、说明、封面和页面链接，不让内容编辑人员直接修改其 HTML/JavaScript 源码。

### 5.1 工艺解决方案编号冲突

当前页面第 03 项是“VOCs尾气回收治理与颗粒活性炭VPS回收装置”。最终需求同时包含：

- 工艺解决方案删除第 03 项；
- 首页四个技术入口必须保留“尾气回收治理技术”。

如果直接按当前编号删除 03，首页“尾气回收治理技术”将没有对应详情页。因此迁移前必须确认“第 03 项”指的是当前页面编号，还是旧资料中的编号。

建议默认方案：后台保留 VOCs/VPS 数据但先不锁定公开状态；通过 `status`、`sort` 和导航关联决定是否展示。这样确认后只需调整数据，不需要改数据库结构。

## 7. Directus 总体数据结构

### 7.1 设计原则

1. Directus 使用 UUID 主键，旧站 ID 单独保留为 `legacy_id`。
2. 所有公开集合统一包含 `status`、`sort`、`slug`、`published_at`。
3. 默认语言为 `zh-CN`；英文使用独立翻译表，不再使用散落的 `titleEn`、`summaryEn`。
4. 图片统一使用 Directus Files，底层存储切换到腾讯云 COS。
5. 删除采用归档，不允许编辑人员物理删除已发布数据。
6. 工艺流程及三维页作为 `interactive_assets` 关联，不把源码写入数据库。
7. 公开 API 只读取 `status = published` 的内容。

### 7.2 通用字段模板

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `status` | String | 是 | draft、in_review、published、archived |
| `sort` | Integer | 是 | 同类内容排序 |
| `slug` | String | 是 | URL稳定标识，唯一 |
| `legacy_id` | String | 否 | 旧 ASP 或 JSON ID |
| `cover_file` | File | 否 | 封面图 |
| `published_at` | DateTime | 否 | 正式发布时间 |
| `date_created` | DateTime | 自动 | Directus系统字段 |
| `user_created` | User | 自动 | Directus系统字段 |
| `date_updated` | DateTime | 自动 | Directus系统字段 |
| `user_updated` | User | 自动 | Directus系统字段 |

### 7.3 翻译表通用字段

每个需要多语言的主集合对应一个翻译表，例如 `articles_translations`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `parent_id` | M2O | 是 | 关联主内容 |
| `language_code` | M2O | 是 | `zh-CN` 或 `en` |
| `title` | String | 是 | 标题 |
| `subtitle` | String | 否 | 副标题 |
| `summary` | Text | 否 | 列表摘要 |
| `body` | Rich Text | 否 | 正文 |
| `seo_title` | String | 否 | SEO标题 |
| `seo_description` | Text | 否 | SEO描述 |
| `translation_status` | String | 是 | missing、draft、reviewed |

主内容与语言组合必须设置唯一约束，避免同一语言重复。

## 9. 留言工作流

```text
新留言
  → 已分派
  → 已联系
  → 跟进中
  → 已完成

任意未完成状态
  → 无效
  → 垃圾留言
```

| 状态 | 含义 | 允许操作角色 |
|---|---|---|
| `new` | 新提交且未处理 | 超级管理员、留言客服 |
| `assigned` | 已指定负责人 | 超级管理员、留言客服 |
| `contacted` | 已首次联系 | 留言客服 |
| `follow_up` | 正在持续跟进 | 留言客服 |
| `completed` | 已完成咨询处理 | 留言客服、超级管理员 |
| `invalid` | 信息无效或重复 | 留言客服、超级管理员 |
| `spam` | 垃圾或恶意提交 | 超级管理员 |

### 9.1 留言接口安全要求

1. 前台提交到独立 `/api/inquiries` 服务，不直接请求 Directus公开创建接口。
2. 启用验证码、IP限流、设备限流、蜜罐字段和服务端字段校验。
3. 手机号、邮箱不得写入前端日志或分析工具。
4. 附件需限制扩展名、MIME、大小并进行安全扫描。
5. 通知失败不能导致留言丢失；先入库，再异步发邮件或企业微信提醒。
6. 导出文件仅允许授权角色下载，并记录导出时间、操作者和筛选条件。
7. 公开接口永远不返回留言详情、总量或连续ID。

## 14. 第一阶段原型范围

### 14.2 证书管理闭环

- 批量上传证书；
- 设置证书分类；
- 去重和排序；
- 同一证书分配到多个展示页面；
- 前台两列紧凑网格；

### 14.3 留言处理闭环

- 表单安全提交；
- 新留言提醒；
- 分派客服；
- 添加备注；
- 修改状态；
- 按条件导出；

## 16. 第一阶段验收标准

1. 超级管理员、内容编辑、新闻编辑、留言客服、只读审阅均能登录且权限正确。
2. 中文是必填默认语言；英文缺失时后台有明确提示，不输出空白页面。
3. 新闻能完成创建、审核、发布、修改和归档。
4. 证书能批量管理，并可同时出现在科研创新和资质荣誉页面。
5. 留言能完成提交、分派、备注、状态变更、提醒和导出。
6. 公共用户无法读取任何留言或后台私有文件。
7. 已发布内容修改有操作记录，编辑人员不能物理删除已发布数据。
8. 前台在后台短时不可用时仍能显示已构建的静态内容。
9. 数据库和媒体文件均有可恢复的备份方案。
